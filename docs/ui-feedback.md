# 조회·요청 상태 UI 규칙

페이지와 폼에서 로딩, 오류, 빈 상태, 처리 결과를 일관되게 표시하기 위한 기준이다.
새로 구현하거나 수정하는 화면에 적용한다. 현재 적용 범위는 아래에 별도로 기록한다.

## 역할 분담

- TanStack Query: 서버 데이터, 조회·변경 요청의 진행 상태, 오류, 캐시, 재시도 관리.
- React 상태: 선택한 항목, 드로어 열림 여부, 입력 중인 값 등 화면 상태 관리.
- 공통 UI 컴포넌트: 로딩·오류·빈 상태·Toast의 모양과 접근성 처리.
- 페이지·폼: 요청이 영향을 주는 범위와 적절한 표시 위치 결정.

같은 요청의 로딩·오류를 별도 `useState`로 중복 관리하지 않는다.
모든 요청을 하나의 페이지 로딩으로 합치지 않고, 같은 응답에 의존하는 영역을 함께 처리한다.

## 페이지 너비

모든 대시보드 페이지의 본문과 로딩·오류·빈 상태는 [PageContainer](../src/components/layout/PageContainer.tsx)를 사용한다.
최대 너비는 개요 기준 `1440px`, 좌우 내부 여백은 `24px`이며 가운데 정렬한다.
작은 화면에서는 가용 너비에 맞춰 줄어든다. 공통 툴바와 수집 현황의 내용도 같은 최대 너비·좌우 여백에 정렬한다. 드로어의 너비는 별도로 유지한다.

## 표시 기준

| 상황                       | 표시 범위와 동작                                                                                                                                                                      |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 최초 페이지 조회           | 해당 응답에 의존하는 본문 전체를 로딩으로 대체한다. 사이드바·헤더 등 공통 틀은 유지한다.                                                                                              |
| 최초 조회 실패             | 해당 본문에 오류 안내와 재시도 버튼을 표시한다. 빈 상태나 정상 지표로 대체하지 않는다.                                                                                                |
| 새로고침                   | 기존 데이터를 유지하고 공통 헤더의 새로고침 버튼에만 스피너와 “조회 중…”을 표시한다. 열려 있는 드로어나 입력값을 초기화하지 않는다.                                                   |
| 새로고침 실패              | 기존 데이터와 본문의 위치를 유지한다. 공통 셸의 작은 고정 알림으로 갱신 실패·마지막 조회 시각·재시도를 표시하고, 본문 위에 오류 패널을 추가하지 않는다. 재조회 성공 시 알림을 없앤다. |
| 상세 조회                  | 드로어로 여는 상세는 클릭 즉시 드로어를 열고 내부에 스켈레톤을 표시한다. 조회 완료 시 같은 드로어에서 본문으로 전환한다. 무관한 본문은 유지한다.                                      |
| 상세 조회 실패             | 열린 드로어 안에서 항목 이름·오류와 상세 재시도를 제공한다. 조회 중·실패 상태에서도 닫을 수 있으며, 늦은 응답으로 다시 열지 않는다.                                                   |
| 저장·삭제 요청 중          | 실행 버튼에 “저장 중…”·“삭제 중…” 등 진행 상태를 표시하고 중복 실행을 막는다. 관련 입력과 충돌하는 동작을 잠근다.                                                                     |
| 처리 성공                  | 서버가 성공을 확정한 뒤 Toast를 표시하고 관련 쿼리를 갱신한다. 완료 후 닫는 폼은 드로어·모달을 닫는다.                                                                                |
| 입력 오류                  | 해당 입력 근처에 오류를 표시한다. 사용자가 입력한 값은 유지한다.                                                                                                                      |
| 저장 실패·동시 수정 충돌   | 폼 안에 오류와 복구 방법을 유지한다. Toast만 띄운 뒤 사라지게 하지 않는다.                                                                                                            |
| 정상 조회 결과가 비어 있음 | 해당 영역에 빈 상태를 표시한다. 가능하면 추가·검색 초기화 등 다음 행동을 제공한다.                                                                                                    |
| 응답 값이 `null`           | 값 자리에 `-`를 표시한다. 로딩이나 실제 값 `0`과 구분한다.                                                                                                                            |

인증·권한이 거부된 경우에는 기존 데이터 유지 규칙보다 접근 제한을 우선한다.
권한 없는 데이터는 숨기고 로그인 또는 권한 안내를 표시한다.

팀 관리의 생성·이름 변경 저장 결과는 성공·실패 모두 Toast로 표시한다. 실패해도 드로어와 입력값은 유지하며, 입력 형식 검증은 입력란 아래에 남긴다. 동시 수정 충돌 시에는 최신 내용 불러오기 버튼을 폼에 유지한다. 실패 Toast는 오류 아이콘과 `role="alert"`를 사용하며, 드로어의 modal dialog 안에서 렌더링한다.

개요·팀·구성원·설정·운영 페이지는 캐시가 있는 요청의 실패/연결 대기를 `useDashboardPageRefresh`로
공통 셸에 전달한다. `RefreshNotice`는 수집 현황의 실패와 합쳐 하나만 표시하며 자동으로 사라지지 않는다.
브라우저 오프라인에 따른 조회 일시 정지는 ‘연결 대기’, HTTP 오류 등은 ‘갱신 실패’로 구분한다.
성공 Toast와 위치를 분리하고 본문·헤더 높이를 바꾸지 않는다. 마지막 조회는 브라우저의 조회 성공 시각이며,
수집 현황의 마지막 수신 시각과 다르다. 수집 현황도 캐시가 있으면 기존 문구를 유지한다.

설정의 지표 카드·벤더 목록·수집 정책·알림 규칙은 같은 설정 응답을 사용하므로
최초 로딩과 조회 실패도 함께 처리한다. 별도 상세 요청은 페이지 전체를 가리지 않는다.
독립된 API를 사용하는 영역은 한 요청이 실패해도 다른 정상 영역을 유지할 수 있다.

## 개요의 부분 실패

단일 응답의 `errors`에 있는 영역만 오류로 표시한다. 페이지 공통 `RefreshNotice`에 재시도를 한 번만 제공하고 정상 영역은 유지한다. 재조회 중에도 기존 화면을 유지하며 새 응답의 실패 영역에 이전 snapshot 값을 섞지 않는다. 지표의 `partial/unavailable`과 비교 불가는 데이터 근거 상태이므로 재시도 알림의 조건이 아니다.

## TanStack Query 상태 사용

- 활성화된 조회에 데이터가 없고 `isPending`이면 최초 조회 상태로 처리한다.
- `data`가 있고 `isFetching`이면 기존 내용을 유지하며 재조회 중임을 표시한다.
- `isError`이면 사용 가능한 기존 데이터 유무에 따라 최초 실패와 갱신 실패를 구분한다.
- 변경 요청은 `useMutation`의 `isPending`으로 진행 표시와 중복 실행 방지를 연결한다.
- 수동 새로고침·조회 재시도는 `refetch({ cancelRefetch: false })`를 사용한다. 같은 쿼리의 요청이 진행 중이면 취소·재시작하지 않고 그 결과를 기다린다.
- 저장·삭제 후 `invalidateQueries`에는 위 옵션을 일괄 적용하지 않는다. 변경 전에 시작한 요청이 있다면 변경 후 데이터를 다시 조회해야 하기 때문이다.
- `enabled: false`인 쿼리도 `isPending`일 수 있다. 선택하지 않은 상세 항목까지 로딩으로 표시하지 않는다.
- 네트워크 문제로 요청이 일시 정지된 상태는 실제 진행 중인 요청과 구분한다. `fetchStatus`를 확인해 연결 대기 상태를 안내한다.

편집 중 서버 재조회로 입력값을 덮어쓰지 않는다. 최신 내용으로 입력을 초기화해야 한다면
사용자의 명시적인 다시 불러오기 동작으로 처리한다.
항목을 전환할 때는 쿼리 키에 조직·항목 ID를 포함하고 요청에 `AbortSignal`을 전달해
이전 응답이 새 선택을 덮어쓰지 않게 한다.

## 성공 Toast

- 화면 하단의 일관된 위치에 표시하며 본문 레이아웃을 밀지 않는다.
- 기본 표시 시간은 4초로 하고, 닫기 버튼을 제공한다.
- 포인터를 올리거나 키보드 초점이 Toast 안에 있으면 자동 닫힘을 잠시 멈춘다.
- 성공 알림은 `role="status"` 등 정중한 라이브 알림으로 전달하고 초점을 강제로 옮기지 않는다.
- 닫기 버튼에는 접근 가능한 이름을 제공한다. 움직임 효과는 모션 감소 설정을 따른다.
- 동일한 작업의 성공 메시지를 본문과 Toast에 중복 표시하지 않는다.
- 연속 알림은 가장 최근 메시지 하나를 표시한다. 같은 문구가 다시 와도 표시 시간을 새로 시작한다.
- 사용자가 실행한 작업 완료에 사용한다. 자동 재조회 성공마다 Toast를 띄우지 않는다.
- 저장 성공 후 목록 갱신만 실패했다면 저장 실패로 안내하지 않는다. 저장 결과와 갱신 실패를 구분한다.

문구 예시: “변경사항을 저장했습니다”, “계약 정보를 비웠습니다”, “벤더를 삭제했습니다”.
사용자가 반드시 읽어야 하는 정책 설명이나 복구 동작은 사라지는 Toast에만 담지 않는다.

## 컴포넌트와 Storybook

공통 표현은 `src/components/ui/`에 두고, 화면은 필요한 상태를 조합한다.
공통 컴포넌트에 특정 API 호출이나 페이지별 권한 판단을 넣지 않는다.
규칙을 바꿀 때는 문서·관련 컴포넌트·Storybook 사례를 함께 갱신한다.

공통 성공 알림은 [Toast.tsx](../src/components/ui/Toast.tsx)의 `Toast`와 [useToast](../src/hooks/ui/use-toast.ts)를 사용한다.
화면에서 `useToast()`를 호출하고 `Toast`를 한 번 렌더링한 뒤, 사용자 작업의 성공 콜백에서
`showToast(message)`를 호출한다. API·캐시 처리는 호출하는 화면에 둔다.
[Toast 스토리](../src/components/ui/Toast.stories.tsx)와 [성공 알림 예시](http://localhost:6006/?path=/story/ui-toast--success)에서 확인한다.

공통 상태 컴포넌트:

- [LoadingState](../src/components/ui/LoadingState.tsx): 최초 조회의 본문 `panel` 로딩과 작은 영역의 `inline` 로딩. 높이와 외부 여백은 사용하는 화면에서 정한다. 페이지 새로고침은 공통 헤더의 Button을 사용한다.
- [ErrorState](../src/components/ui/ErrorState.tsx): 오류 아이콘·메시지와 선택적인 `description`·재시도 버튼. 패널은 중립적인 카드에 오류 아이콘만 붉게 강조하고 메시지 아래에 복구 동작을 배치한다. `inline`은 헤더 등 작은 영역의 한 줄 표현을 유지한다. `retrying`이면 버튼을 잠근다. 충돌 복구 같은 별도 동작은 `children`으로 조합한다.
- [EmptyState](../src/components/ui/EmptyState.tsx): 빈 결과의 아이콘·메시지·설명·선택적인 다음 행동. 기본 `variant="empty"`는 정상 조회의 빈 결과, `variant="not-connected"`는 아직 제품을 연결하지 않은 상태에 사용한다. 미연동은 연결 아이콘과 주요 연결 동작으로 안내하며, 조회 실패나 연결 후 첫 데이터 대기와 구분한다. 연결 여부 판단과 실제 연결 동작은 호출하는 화면에서 제공한다.
- [PeriodEmptyState](../src/components/ui/PeriodEmptyState.tsx): 개요·팀 분석의 기간 조회 결과가 없을 때 사용한다. 본문 전체 너비, 최소 높이 240px, 가운데 아이콘과 ‘선택한 기간에 데이터가 없습니다’·‘다른 기간을 선택해 주세요.’를 동일하게 표시하고 지표·차트·요약은 숨긴다. 팀의 사용자별 사용량이 비었을 때도 같은 컴포넌트를 쓰되 팀 선택 안내를 함께 제공한다. 최초 수집 안내와 조회 오류는 별도로 유지한다.
- [Button](../src/components/ui/Button.tsx): `loading`과 `loadingLabel`로 진행 표시·버튼 잠금·`aria-busy`를 함께 처리한다.
- [공통 상태 스토리](../src/components/ui/Feedback.stories.tsx): [UI / Feedback](http://localhost:6006/?path=/story/ui-feedback--page-loading).

공통 컴포넌트는 쿼리를 직접 받지 않는다. 페이지에서 데이터 유무·권한·요청 상태에 따라
필요한 표현을 선택하며, 로딩만을 위한 별도 서버 상태나 페이지별 복제 컴포넌트를 만들지 않는다.

현재 설정 구현:

- [SettingsContent](../src/components/settings/SettingsContent.tsx): 본문 조회 상태, 새로고침, 벤더 상세 조회.
- [VendorTable](../src/components/settings/VendorTable.tsx): 계약 설정 드로어를 즉시 여는 행.
- [ServerVendorDrawer](../src/components/settings/ServerVendorDrawer.tsx): 상세 조회 스켈레톤·오류·재시도, 변경 요청, 입력 보존, 충돌 복구.
- [설정 스토리](../src/components/settings/SettingsContent.stories.tsx): 상태별 상호작용 검증.

`Pages` 아래 개요·팀 분석·구성원·운영·보안·설정을 페이지별로 묶고, 각 페이지에 `일반 / 로딩 / 에러`를 둔다.
실제 페이지 컴포넌트와 공통 헤더를 사용하며 MSW 응답으로 상태를 재현한다.
`에러`의 Controls → **에러 상황**에서 `최초 조회 실패 / 갱신 실패`를 전환한다.
최초 실패에는 본문 오류가, 갱신 실패에는 마지막 정상 데이터와 고정 갱신 알림이 표시된다.
에러 응답은 스토리에서 유지되므로 재시도해도 실패한다. 일반 상태는 `일반` 항목에서 확인한다.

## 적용 현황

설정의 최초 본문 로딩, 기존 데이터를 유지하는 재조회, 벤더 상세 조회는 구현되어 있다.
저장 오류와 충돌 안내도 드로어 안에서 처리한다. 위 Storybook은 목 API로 동작하며,
실제 서버 연동 검증은 별도 E2E 테스트에서 수행한다.

공통 성공 Toast를 구현하고 설정의 벤더 추가·저장·계약 비우기·삭제와 수집 정책 저장에 적용했다.
공통 로딩·오류·빈 상태 컴포넌트를 설정 본문·미적용 설치 목록과 개요 본문에 적용했다.
설정 드로어의 오류 표시, 저장·삭제 버튼과 수동 새로고침 버튼도 공통 표현을 사용한다.
개요의 관측 안내처럼 도메인 설명이 필요한 빈 상태는 기존 전용 컴포넌트를 유지한다.
구성원 화면은 명단·요약·미배정을 한 snapshot의 조회로 묶어 본문 로딩·오류·재조회를 함께 처리하고,
초대 대기와 팀 목록은 독립 조회라 한쪽이 실패해도 명단을 유지한다. 필터·정렬·검색·CSV는 전체 페이지를 받은 명단에 적용한다.
구성원 화면의 저장(팀·역할 편집, 팀 배정, 팀 관리, 초대 코드)은 서버가 확정하고 관련 조회를 다시 읽은 뒤에 화면을 바꾼다.
편집기는 열었을 때의 version으로 저장하고, 충돌하면 입력을 남긴 채 잠그고 “최신 내용 불러오기”를 눌렀을 때만 최신 값으로 바꾼다.
팀·역할 저장, 팀 배정, 초대 취소와 다시 보내기·코드 재발급의 처리 성공은 Toast로 알린다.
다시 보내기 접수는 “발송 대기열에 넣었습니다”로 알리고 실제 발송 상태와 구분한다. 같은 성공 문구를 행에 중복 표시하지 않는다.
발급·재발급한 초대 코드는 다시 조회할 수 없는 값이라 Toast가 아닌
그 자리(초대 창·대기 행)에 남기고, 초대 창을 닫거나 행에서 숨기면 화면에서 지운다. 팀 관리는 드로어 안의 안내로 결과를 알린다.
초대 메일의 상태는 서버의 `delivery`를 그대로 옮긴다 — 발송 대기·발송 중·재시도 대기(사유)·발송됨(시각)·실패(사유)·취소됨·발송 꺼짐·보낸 메일 없음.
발송이 끝나지 않은 초대가 있는 동안에는 초대 목록만 짧은 주기로 다시 읽어 발송 결과를 반영한다(명단은 다시 읽지 않는다).
다시 보내기와 초대 취소는 되돌릴 수 없어 행 안에서 한 번 더 확인한다.
초대 수락 화면은 회사 SSO 로그인을 안내한다. 초대 코드는 CLI 설치용이며 비밀번호 가입에 사용하지 않는다.
도입 문의 폼은 입력 확인과 접수를 나눈다. 확인 단계에서는 요청을 보내지 않고, 접수 버튼은 요청 중에 잠그며,
접수 번호와 시각은 사라지지 않게 그 자리에 남긴다(Toast를 쓰지 않는다). 실패하면 입력을 남긴 채 사유(입력 오류·요청 한도의 대기 시간·연결 실패)를 폼 안에 보여 준다.
갱신 실패 문구, 네트워크 연결 대기 표시와 다른 페이지의 적용 여부는 추가 점검이 필요하다.
이 문서를 추가한 것만으로 모든 화면이 기준을 충족한 것으로 보지 않는다.

## 공통 헤더의 조직 수집 현황

`DashboardHeaderProvider`는 대시보드 레이아웃에서 한 번만 렌더링한다. 기간 필터와
자동 갱신 설정도 같은 레이아웃의 `FiltersProvider`를 사용하며 페이지별로 중첩하지 않는다.
5분 자동 갱신의 켜짐/꺼짐은 `localStorage`의 `pulsemetry.autoRefresh`에 `true`/`false`로 저장한다. 기본값은 꺼짐이며, 새로고침·재접속 시 복원하고 같은 출처의 다른 탭에도 반영한다. 저장소를 사용할 수 없으면 현재 탭의 메모리에서만 유지한다.
페이지는 `useDashboardPageRefresh`로 자신의 재조회 동작·진행 여부만 등록한다.
수동 새로고침은 현재 페이지와 조직 수집 현황을 함께 조회하고, 자동 갱신은 공통 설정을 따른다.
개요·팀 분석·구성원·운영·보안·설정의 재조회 진행 표시는 `FilterToolbar`의 새로고침 버튼으로 통일한다.
페이지 또는 수집 현황의 조회가 진행 중이면 버튼에 스피너와 “조회 중…”을 표시하고 중복 실행을 막는다.
본문 제목 옆 안내와 수집 현황의 별도 갱신 스피너는 표시하지 않는다. 최초 조회·오류·상세 조회의 영역별 표시는 유지한다.
운영·보안은 현재 알림 상태 필터의 보안 알림 목록을 공통 버튼에 연결한다.

`IngestStatusBar`는 공통 헤더 왼쪽에 표시하고 알림·테마는 오른쪽에 둔다. 헤더는 최소 64px이며 좁은 화면에서 수집 안내가 줄바꿈된다. 조직 ID만 포함한 쿼리 키로
`GET /api/v1/organizations/{organizationId}/ingest-status`를 조회하므로 기간 변경과 독립적이다.
최초 조회는 inline LoadingState, 오류는 inline ErrorState를 쓴다. 재조회는 기존 값을 유지하고 공통 새로고침 버튼에 진행 상태를 표시한다.
권한 거부 시 이전 값은 숨기고 조직이 바뀌면 다른 조직의 캐시를 표시하지 않는다.
현재 서버 판정은 empty/unknown이며 lastReceivedAt만으로 정상·지연·중단을 추정하지 않는다.
마지막 수신 시각은 한국 시간의 절대 시각으로 표시해 자동 갱신을 꺼도 상대 시간이 낡지 않게 한다.
개요의 선택 기간별 관측 일수는 헤더가 아닌 개요 본문에서 표시한다.

[공통 헤더 스토리](../src/components/layout/DashboardHeader.stories.tsx)에서 로딩·오류·재시도·재조회·본문 전환을 검증한다.
수집 현황은 백엔드의 수집 상태 조회(`GET /api/v1/organizations/{organizationId}/ingest-status` — 백엔드 대시보드 명세 "공통 헤더 수집 현황", ADR 0041)의
판정·사유·보고 중인 설치 수를 그대로 보여 준다. 조회가 실패하면 오류를 표시하고 목 응답으로 대체하지 않는다.

백엔드 저장소에서 패치 적용 확인과 적용 후 테스트:

```powershell
git apply --check ../pulsemetry-frontend/patches/backend-ingest-status.patch
git apply ../pulsemetry-frontend/patches/backend-ingest-status.patch
./gradlew.bat :apps:dashboard-api:test --tests '*IngestStatusApiTest'
```

### 분석 페이지의 날짜·비교 조건과 복원

개요·팀 분석의 `startDate`, `endDate`, `compare` 쿼리 파라미터가 페이지 조회 도구와 API 요청의 기준이다.
구성원·운영·설정 URL에는 이 세 파라미터를 붙이지 않으며, 예전 링크로 접속해도 세 조건만 제거한다.
공통 레이아웃이 마지막 분석 조건을 메모리에 보관해 페이지 이동 후 복원한다. 분석 URL에 명시된 조건은 기억한 값보다 우선한다.
관리 페이지에서 새로고침하거나 새 탭으로 열면 메모리의 선택은 초기화되며, 다음 분석 페이지는 기본값을 사용한다.
기본값은 한국 시간 기준 이번 주 월요일부터 오늘까지, 비교는 `prev_week`다.
전주 비교는 백엔드 계약대로 선택 기간의 양 끝을 7일 이전으로 옮긴 같은 길이의 기간이다.
기본값도 URL에 기록하므로 공유하거나 새로고침할 때 조회 기간이 바뀌지 않는다.

달력에서 ‘적용’을 누르거나 비교를 바꾸면 `history.replaceState`로 현재 방문 기록을 갱신한다.
개요·팀 분석으로 가는 이동 링크만 마지막 선택 조건을 전달한다. 목적지의 `vendor`, `team`, `invite`와 해시는
보존하고, 드로어를 닫을 때는 해당 드로어의 파라미터만 지운다.
날짜는 실제 존재하는 YYYY-MM-DD와 종료일 포함 1~366일을 검증한다.
누락·역전·중복 등 유효하지 않은 기간은 이번 주로, 유효하지 않은 비교는 전주로 복구한다.
미래 날짜는 백엔드와 동일하게 허용하며 데이터 부재는 조회 결과로 표시한다.

사이드바의 로그아웃은 로그인한 계정의 역할 배지 옆 버튼이다. 접힌 상태에서는 아이콘 버튼으로
제공하며 접근 가능한 이름은 ‘로그아웃’을 유지한다. 요청 중·429 대기 중에는 중복 요청을 막는다.

### 초대의 사용 예정 제품

일반 초대·온보딩은 같은 복수 선택 UI를 사용한다. 기본 선택과 개인별 선택을 구분하고 개인별 선택을 지우면 미선택, ‘기본 선택 사용’은 상속으로 복원한다.
제품 목록 조회 실패를 빈 목록으로 표현하지 않는다. 재시도 UI를 제공하며 저장 요청 실패 시 입력은 보존한다. 발급 중에는 초대 대상과 선택값을 잠근다.
사용 예정 제품은 실제 벤더 좌석과 분리해 구성원 상세에서도 수정한다.

### 페이지별 최초 로딩 스켈레톤

개요·팀 분석·구성원·설정은 데이터가 없는 최초 조회에 각 페이지의 `*Skeleton`을 사용한다.
공통 `Skeleton.tsx`의 블록·카드·행·차트 부품을 조합하고 실제 본문의 열 수와 반응형 분기점을 맞춘다.
페이지 제목·공통 헤더·사이드바는 유지한다. 스켈레톤은 API나 쿼리 상태를 소유하지 않는다.
기존 데이터가 있는 재조회에는 스켈레톤으로 되돌리지 않고 공통 새로고침 버튼만 진행 상태로 표시한다.

장식 블록은 보조기기에서 숨기고 `SkeletonRegion`이 기존 로딩 문구를 `role="status"`로 한 번 알린다.
모션 감소 설정에서는 펄스 애니메이션을 끈다. 벤더 계약 상세는 `VendorContractSkeleton`을 사용하며, 작은 영역의 로딩에는 `LoadingState`를 사용한다.

각 페이지의 `로딩` 스토리(예: [Pages / 개요 / 로딩](http://localhost:6006/?path=/story/pages-overview--loading))에서 스켈레톤을
백엔드 없이 확인할 수 있다. 테마 선택과 브라우저 너비 변경으로 다크 모드와 반응형 배치를 확인한다.
설정의 기존 `Loading`, `LoadingThenLoaded`, `Refreshing` 스토리에서도 실제 조회 전환을 확인할 수 있다.

### 개요 지표 안내

개요의 KPI 위에는 관측 일수와 기간 비교 제한 안내 문구를 표시하지 않는다.
마지막 수신 시각은 공통 헤더에만 남기며, 헤더에는 연도를 포함한 날짜와 시각을 표시하고 보고 기기 수는 표시하지 않는다.
전체 시각·수집 사유는 도움말에 유지한다. KPI는 현재 값의 ‘집계 중’·‘관측 근거 부족’·‘일부 집계’·‘값 확인 불가’ 상태를 제목 옆에, 증감을 계산할 수 없으면 ‘비교 불가’를 값 아래에 표시한다.
현재 값이 없는 경우에는 ‘값 확인 불가’만 표시하며, 비교를 끄면 비교 배지를 표시하지 않는다. 긴 사유는 배지에 포인터를 올리거나 키보드 초점을 줄 때 보여 준다.
KPI 제목·값·설명은 가용 너비에 맞춰 줄바꿈하고, 세션 수에는 ‘개’를 붙인다.
총 토큰 수가 미확정이면 단위 없이 `-`와 ‘전체 토큰 수를 확인할 수 없습니다’를 표시한다.

### 페이지 헤더

개요·팀 분석·구성원·운영·보안·설정은 `PageHeader`를 사용한다.
제목(22px)만 표시하며 페이지별 소개 문구는 두지 않는다. 팀 관리·구성원 초대 등 페이지 작업은 오른쪽에 배치한다.
모든 페이지의 상단 여백(24px)과 다음 영역과 간격(24px)을 통일하며, 헤더 하단 구분선은 두지 않는다.
데이터 주의사항은 헤더 다음의 본문 안내로 표시한다. 팀 분석에는 선택 조건을 반복하는 안내 문구를 두지 않는다.
로딩·오류 상태에서도 같은 제목을 유지한다. 좁은 화면에서는 제목과 작업 버튼이 줄바꿈된다.

개요·팀 분석은 페이지 제목 바로 옆에 날짜·비교 선택을 배치하고, 좁은 화면에서는 줄바꿈한다. 관리 페이지에는 날짜·비교 선택을 두지 않는다.
새로고침·자동 갱신·CSV·알림·테마는 공통 헤더 오른쪽에 유지한다.
`Layout / PageHeader` Storybook에서 다섯 페이지와 좁은 화면 배치를 확인할 수 있다.

### 알림 검사 정보

알림 드로어 제목 옆에는 선택한 상태의 알림 건수를 표시하고 본문 하단에는 중복 표시하지 않는다. 제목 아래에는 목록 응답의 `meta.asOf`를 한국 시간으로 ‘YYYY년 M월 D일 H시 기준’ 형식으로 표시한다. 로딩 중에도 해당 줄의 공간을 유지한다. 검사 정보 영역과 규칙별 검사 사유는 표시하지 않는다.

### 계약 입력 안내

헤더는 기간과 무관한 `contract-input-status`를 읽어 ‘계약 입력 필요 N건’을 표시한다. 클릭하면 `/settings?vendor={첫 미입력 vendorId}`로 이동해 계약 편집창을 바로 연다. 설정 상단의 별도 안내 섹션은 두지 않는다. 등록된 계약이 없을 때만 세며, 만료·시작 예정·0달러 계약은 제외한다. 조회 실패를 0건으로 숨기지 않고 재시도를 제공한다. 설정은 벤더별 플랜·좌석 수·월 좌석 단가 입력 필요 항목을 표시하고, 드로어에서는 초안의 남은 항목을 표시한다. 저장 성공 시 조직 쿼리를 무효화하며 완료되면 헤더 안내를 숨긴다.

### 계약 만료 알림

공통 알림 종은 미확인 보안·비용 알림과 현재 만료 계약의 건수를 합산한다. 계약 미입력 안내와 같은 `contract-input-status` 캐시를 사용하고 설정 전체를 미리 조회하지 않는다. 로딩은 `…`, 조회 실패는 `!`로 표시하며 확인하지 못한 값을 0건으로 안내하지 않는다.

알림 드로어의 `미확인`·`전체`에는 “만료된 계약이 있습니다”와 벤더 이름·계약 종료일·“계약 갱신” 링크를 보여 준다. 클릭하면 드로어를 닫고 해당 벤더의 설정 계약 폼으로 이동한다. `확인함`에는 표시하지 않는다. 갱신으로 해소하는 현재 상태이므로 별도 확인 버튼을 두지 않으며, 저장 성공 후 조직 조회 캐시를 갱신해 만료 상태가 해소되면 사라진다.

계약 만료 조회의 로딩·오류·재시도는 드로어 안에 따로 표시하고 정상 보안·비용 알림은 유지한다. 만료 계약이 있는데 “미확인 알림이 없습니다”를 함께 표시하지 않는다. 긴 벤더 이름은 줄바꿈하며 갱신 링크를 가리지 않는다.

`Layout / DashboardHeader`의 `만료된 계약 · 계약 갱신 링크`, `계약 만료 조회 실패 · 다른 알림 유지`, `계약 만료 조회 중 · 다른 알림 유지`와 설정의 `만료 계약 갱신 · 알림 해소` 스토리에서 확인한다.

### 사용 추이의 0과 확인 불가

개요와 팀 분석은 `TrendFeedback`으로 끝점·누락 구간·날짜별 툴팁을 공유한다.
수집 근거가 확인된 0은 실제 값으로 그린다. 일별 값은 0, 누적 값은 이전 값과 같은 높이를 유지한다.
사용 관측이 없고 완전성 근거도 없으면 미사용과 수집 공백을 구분할 수 없으므로 ‘사용량 확인 불가’로 표시한다.
휴일·주말이라는 이유로 0을 채우거나, 기기 보고가 없다는 이유만으로 장애·수집 중단이라고 표현하지 않는다.
누적값이 앞선 날짜의 누락 때문에 계산 불가능하면 ‘누적값 확인 불가’로 표시한다. 실제 원인은 날짜별 툴팁에서 설명한다.
부분 관측 값은 기존 집계를 유지하되 ‘일부 집계’와 실제 사용량과 다를 수 있다는 설명을 제공한다.
미래 날짜는 확인 불가 구간과 배지 판정에서 제외하며 툴팁에 아직 도래하지 않은 날짜로 안내한다.
각 계열의 마지막 표시 지점을 점으로 표시하고, 배지 상세에서 팀별 표시 종료일을 제공한다.
날짜 탐색은 포인터·방향키·Home·End를 지원하고 Escape로 상세를 닫는다.
`Charts / 사용 추이 상태` 스토리에서 확인된 0, 휴일 관측 부재, 팀별 종료일 차이, 미래를 비교한다.
