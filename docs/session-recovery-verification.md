# 단일 BFF 운영 결정과 세션 폐기 후 복구 검증

2026년 10월 17일 로컬 브라우저에서 세션 폐기 후 로그인 화면으로 이동하고, 재로그인 후 대시보드를 다시 조회하는 흐름을 확인했다. 단일 BFF 운영 정책과 애플리케이션 구현은 변경하지 않았다. 추가한 것은 재현 가능한 브라우저 테스트와 증거다.

## 결정과 근거

현 단계에서는 단일 Node 프로세스와 ECS 태스크 1개를 유지한다. 배포 중 중단과 일부 세션의 재로그인을 허용하고, 다중 인스턴스 갱신 공유는 도입하지 않는다.

- [인프라 설정](../../infra/frontend/modules/application/main.tf)은 개발 EC2와 운영 Fargate 모두 desired_count=1, minimumHealthyPercent=0, maximumPercent=100이다. [ADR 0028](../../infra/docs/adr/0028-frontend-alb-and-container-runtime.md)도 BFF 메모리 갱신 조율 때문에 중단을 허용하는 배포를 선택했다.
- [이전 재현](bff-refresh-reproduction.md)에서 단일 BFF의 동시 20개 요청은 갱신 1회로 성공했고, 독립 BFF 두 개의 중첩 갱신은 모의 백엔드에서 세션을 폐기했다.
- 현재 프로젝트에서 무중단 배포·자동 확장을 필수로 요구하지 않는다는 전제다. Redis 등을 도입하면 갱신 락뿐 아니라 결과 전달, 작업 소유자 장애, 토큰 보관, 저장소 장애까지 다뤄야 한다.
- 단일 프로세스에서도 응답 유실 후 캐시 만료에 따른 재로그인은 남는다. 이번 검증은 이 실패를 없애는 대신, 폐기된 세션에서 다시 로그인해 사용할 수 있는지를 확인한다.

이 결정은 저장소 설정을 근거로 한다. AWS 실배포의 태스크 수, 종료·draining 순서, 배포 중단 시간은 이번에 조회하거나 측정하지 않았다. 컨테이너 하나에서 여러 Node worker를 실행해도 메모리가 분리되므로 프로세스 수 역시 하나여야 한다.

## 검증 경계

실제 Google Chrome → 실제 Next.js production 서버 → 실제 BFF HTTP 경로 → 테스트용 인증·업무 HTTP 서버 → 실제 화면 렌더링을 검증했다. 브라우저의 page.route로 BFF 응답을 가로채거나 브라우저에 세션 쿠키를 직접 주입하지 않았다.

회사 인증 단계는 이름이 명시된 모의 인증 페이지로 대체했다. 사용자가 로그인 폼을 제출하면 모의 페이지로 이동하고, 테스트 인증 완료 링크로 실제 프론트 콜백을 처리한다. 테스트 서버는 일회용 코드와 PKCE challenge/verifier를 대조하며 BFF가 사용자 확인과 쿠키 발급을 수행한다. 실제 Cognito 신원 확인, Spring/DB 토큰 로직, HTTPS 쿠키 설정은 이 실험으로 검증되지 않는다.

세션 폐기는 모의 서버의 활성 상태를 false로 바꿔 주입했다. 이번 브라우저 테스트가 RT 재사용이나 응답 유실 자체를 일으킨 것은 아니다. 그 실패 조건의 재현은 이전 테스트이고, 이번 것은 폐기 이후 복구 구간의 검증이다.

## 시나리오와 결과

| 단계                       | 통과 기준                                             | 관찰 결과                                      |
| -------------------------- | ----------------------------------------------------- | ---------------------------------------------- |
| 최초 로그인                | 폼 → 모의 인증 → 실제 콜백 → BFF 쿠키 발급 → 조회     | 성공, 세션 1, 사용 환산액 $5,000.00 렌더링     |
| 세션 폐기 후 수동 새로고침 | 업무 API 401 이후 보호 화면 제거 및 로그인 화면 이동  | 성공, 개요 API와 refresh가 401, 로그인 폼 표시 |
| 폐기 쿠키가 남은 상태      | 쿠키를 직접 삭제하지 않고도 로그인 화면 이용 가능     | 이전 HttpOnly 쿠키 유지 확인                   |
| 로그인 화면 새로고침       | 보호 화면과 로그인 화면의 반복 이동 없이 폼 사용 가능 | 성공                                           |
| 재로그인                   | 폼과 모의 인증을 다시 거쳐 새 쿠키 발급               | 성공, 세션 2, 쿠키 값 변경 및 HttpOnly 확인    |
| 정상 조회 복구             | 새 세션으로 API 200 및 화면 데이터 표시               | 성공                                           |
| 복구 후 수동 새로고침      | 캐시 표시만이 아니라 추가 API 200 발생                | 성공, 세션 2의 개요 200 요청이 추가됨          |
| 브라우저 실행 오류         | pageerror 없음                                        | 0건                                            |

“로그인 안내”의 현재 형태는 **회사 계정으로 로그인 화면으로 이동하는 것**이다. 별도의 “세션이 만료되었습니다” 사유 문구는 현재 표시되지 않는다. 원인 안내까지 구현·검증했다고 표현하지 않는다. pageerror 0건은 콘솔·네트워크 오류 전체가 0이라는 뜻이 아니다. 401은 의도적으로 주입했고, 모의 인증 서버의 favicon 요청에도 401이 기록돼 있다.

- [재로그인 후 조회 화면](evidence/session-recovery/03-recovered.png)
- [모의 upstream 요청 기록](evidence/session-recovery/upstream-events.json): 경로, 상태 코드, 세션 세대만 기록하며 토큰·쿠키는 기록하지 않는다. session=1/2는 모의 서버의 세대 번호다.
- [브라우저 테스트](../tests/browser/session-recovery.spec.ts)

기록에서 개요 응답은 세션 1의 200 → 401 → 세션 2의 200 → 수동 새로고침 200 순서다. 재로그인 중 `/auth/logout` 204는 BFF가 이전 쿠키의 세션을 정리하는 호출이며 새 세션을 폐기한 것이 아니다.

## 실행 환경과 재실행

Node.js v24.18.1, 설치된 Google Chrome, Playwright를 사용했다. 기존 작업 트리의 미커밋 변경을 포함한 소스를 `/tmp/pulsemetry-recovery.dnBtQ5`로 복사하고 `.env*`, `.git`, `.next`를 제외했다. 원본의 빌드 산출물과 개발 서버에 영향을 주지 않기 위한 격리다. node_modules는 원본 설치 경로를 연결했다.

검증 포트는 Next.js 3107, 모의 upstream 3110이며 실행 전에 비어 있음을 확인했다. 임시 복사본에서 webpack production 빌드를 사용했고, 서버는 127.0.0.1에 바인딩했다. 기존 mock 설정의 공개 enrollment 주소를 빌드 시 주입했다. 실제 운영 이미지 빌드·Turbopack 검증을 의미하지 않는다.

처음 서버 실행은 샌드박스의 포트 listen 제한으로 실패했다. 로컬 서버·브라우저 실행 권한으로 재실행해 브라우저 테스트 1개가 통과했다. 실행 결과는 `1 passed (6.2s)`이며 이는 테스트 도구 실행 시간이지 사용자 복구 시간 측정값이 아니다. 테스트 종료 후 두 검증 포트에 리스너가 없음을 확인했다.

독립된 체크아웃에서 두 포트가 비어 있음을 확인한 뒤 다음 테스트만 실행한다. 다른 3110 사용 테스트 파일과 동시에 실행하지 않는다.

```sh
PLAYWRIGHT_CHROMIUM_EXECUTABLE='/Applications/Google Chrome.app/Contents/MacOS/Google Chrome' \
  npx --no-install playwright test --config=playwright.mock.config.ts \
  session-recovery.spec.ts --workers=1 --trace=on
```

위 저장소 설정은 기본 빌드 명령을 사용한다. 이번 실행의 임시 복사본에서는 symlink된 의존성을 사용하기 위해 빌드 명령을 `npm run build -- --webpack`으로 바꿨고, 빌드 완료 후 `npm run start -- --hostname 127.0.0.1 --port 3107`로 실행했다. 검증용 설정 변경은 저장소에 반영하지 않았다. Trace는 임시 폴더의 `recovery-trace.zip`에 남겨 두었으며 fixture 쿠키가 포함될 수 있어 저장소 증거에는 화면과 비밀값 없는 요청 기록만 남겼다.

추가 검사: `npm run format:check`, `npm run lint`, `npm run typecheck` 모두 통과했다.

## 한계와 재검토 조건

- 현재 검증은 새로고침 버튼으로 세션 폐기를 감지하는 한 브라우저 흐름이다. 입력 중 폼 보존, 모든 탭 간 동기화, 모든 API 실패 경로를 포괄하지 않는다.
- 재로그인은 가능하지만 사용자가 왜 로그인 화면으로 이동했는지 설명하는 문구는 없다. 필요하다면 인증 실패 이유를 안전하게 전달하는 별도 UX 개선으로 다룬다.
- 가용성·실사용자 수·복구 시간 개선을 측정하지 않았다. 배포 중 중단과 재로그인을 감수하는 조건부 운영 선택이다.
- 무중단 배포, 장애 시 연속 서비스, 측정된 용량 부족이 요구되면 공유 갱신 조율을 재검토한다. 응답 유실 복구 보장이 필요하면 백엔드의 토큰 회전 계약까지 함께 검토한다.

## 포트폴리오 설명

“BFF의 갱신 조율이 프로세스 메모리에 의존하는 제약을 확인하고, 무중단·다중 인스턴스 운영 대신 기존 단일 프로세스 배포 정책을 유지했다. 남는 세션 단절에 대해서는 실제 Next.js와 브라우저, 모의 인증·업무 서버로 세션 폐기 후 로그인 화면 이동, 재로그인, 새 세션의 API 조회 복구를 검증했다.”

이번 테스트는 AI와 함께 추가·실행한 검증이다. 기존 인증 설계의 기여, 이번 운영 판단, 테스트 작성·해석의 본인 역할을 구분해 설명한다. 분산 인증 해결, 실제 Cognito 장애 복구 검증, 무중단 운영 달성으로 표현하지 않는다.
