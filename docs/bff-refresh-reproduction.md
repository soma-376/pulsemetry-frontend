# BFF 동시 갱신과 인스턴스 분리 재현

2026년 10월 17일 로컬에서 실제 `createBff` 구현을 호출해 단일 인스턴스의 갱신 공유와 독립 인스턴스 사이의 충돌을 재현했다. 독립 BFF 두 개가 같은 RT를 갱신하면 모의 백엔드의 재사용 탐지로 세션이 폐기되고 두 요청이 401로 끝났다. 운영 코드는 변경하지 않았다.

## 검증 범위와 환경

- 기준 frontend HEAD: `4afd0ebb9a35723017c727038392814bfd0864fa`. 기존 미커밋 작업이 있는 작업 트리에서 실행했다.
- Node.js v24.18.1과 tsx를 사용하는 Node 테스트 러너. 별도 서버나 포트는 사용하지 않는다.
- 실제 대상: `src/lib/server/bff.ts`, `src/lib/server/session-cookie.ts`.
- 두 인스턴스는 한 Node 프로세스에서 별도로 생성한 `createBff` 객체다. 동일 origin과 암호화 키, 같은 쿠키, 같은 모의 백엔드를 사용하지만 각 객체의 refresh Map은 독립적이다.
- 모의 백엔드는 `UserAuthService.rotate`의 세션 잠금 안에서 수행하는 RT 소비·재사용 시 세션 폐기와 `UserAccessVerifier.verify`의 폐기된 세션 거부를 모델링한다. 모의 구현은 임계 구역에서 await하지 않아 소비와 폐기를 원자적으로 처리한다.
- JWT 서명, DB 트랜잭션, HTTP 전송, Next 서버 두 프로세스, ALB, 실제 Cognito 로그인은 이 실험의 검증 대상이 아니다. 로그인 대신 테스트용 만료 AT·RT로 실제 쿠키 코덱을 사용해 쿠키를 만든다.
- 시계와 응답 순서를 제어한다. 부하 테스트나 시간 성능 측정이 아니다. 대기 중 갱신 응답을 보류해 중첩을 만들며 임의 sleep에 의존하지 않는다.

## 현재 갱신 처리

1. 쿠키를 복호화하고 RT의 SHA-256 해시로 현재 BFF의 refresh Map을 조회한다.
2. 이미 진행 중이거나 유예 중인 갱신이 있으면 그 Promise를 공유한다.
3. 없고 AT가 만료됐거나 만료까지 5초 이내이면 백엔드에 갱신을 요청한다. 만료 전 AT로 보낸 업무 요청이 401인 경우에도 갱신 후 한 번 재요청한다.
4. 갱신 성공 결과는 5초간 유지한다. 갱신된 세션으로 업무 요청을 보내고 응답에 새 쿠키를 담는다.
5. 갱신 후에도 업무 API가 401이면 재갱신을 반복하지 않고 캐시를 무효화해 401을 반환한다.

이 5초는 과거 RT의 백엔드 유효기간을 연장하지 않는다. 같은 BFF가 이미 받은 새 토큰을 공유하는 기간이다. 암호화 키가 같아도 이 Map은 공유되지 않는다.

## 재현 결과

| 조건                                                                     | 갱신 호출 | 요청 결과            | 백엔드 세션 |
| ------------------------------------------------------------------------ | --------- | -------------------- | ----------- |
| 한 BFF에 동시 20개 요청                                                  | 1회       | 20개 모두 200        | 유효        |
| 같은 BFF에 유예 내 이전 쿠키로 추가 요청                                 | 누적 1회  | 200                  | 유효        |
| 독립 BFF A와 B에서 같은 쿠키로 중첩 요청                                 | 2회       | A와 B 모두 401       | 폐기        |
| 그 후 이전 쿠키로 추가 요청                                              | 누적 3회  | 401                  | 폐기 유지   |
| 한 BFF의 성공 응답을 받지 못했다고 가정하고 5001ms 후 이전 쿠키로 재요청 | 2회       | 최초 200, 재요청 401 | 폐기        |

응답 유실 실험에서는 서버가 발급한 새 쿠키도 별도로 보관했다. 폐기 후 그 새 쿠키로 조회해도 401이었다. 새로운 AT가 있어도 백엔드 세션이 폐기되면 사용할 수 없음을 확인한다. 이 추가 요청은 AT 조회의 401 이후 갱신을 시도해 누적 갱신 횟수가 3회가 된다.

## 두 인스턴스에서 실패하는 순서

```text
A와 B가 같은 이전 쿠키를 받음
A: 자기 Map에 갱신 Promise 등록
백엔드: RT0 소비, AT1/RT1 발급 후 응답 전달 보류
B: 자기 Map에는 A의 작업이 없으므로 RT0으로 별도 갱신
백엔드: 이미 소비한 RT0 감지 → 세션 폐기 → B에 401
A: 보류한 AT1/RT1 응답 수신 → AT1으로 업무 API 요청
백엔드: 세션이 폐기됐으므로 A에도 401
```

이 스케줄에서는 두 요청 모두 새 쿠키 없이 401이 된다. 모든 실제 스케줄에서 최초 두 응답이 반드시 401인 것은 아니다. A의 업무 조회가 폐기 전에 끝나면 A는 먼저 200을 받을 수 있다. 본 실험은 실패 가능한 한 실행 순서를 결정적으로 재현한다.

## 실행과 증거

frontend 디렉터리에서 실행한다.

```sh
node --import tsx --test tests/bff-refresh-instances.test.ts
```

3개 테스트가 통과해야 한다. 두 번째·세 번째 테스트의 통과는 장애가 해결됐다는 뜻이 아니라, 예상한 실패 조건을 재현했다는 뜻이다. 진단 출력은 갱신 횟수, 세션 폐기 여부, 이벤트 순서를 포함하며 쿠키와 토큰 원문을 출력하지 않는다.

테스트: [bff-refresh-instances.test.ts](../tests/bff-refresh-instances.test.ts)

실행 결과는 신규 재현 3개와 기존 BFF 18개를 함께 실행해 총 21개 통과, 실패 0개였다. `npm run format:check`, `npm run lint`, `npm run typecheck`도 모두 통과했다.

두 인스턴스 실험의 동시 응답 직후 진단 출력:

```json
{
  "phase": "concurrent responses",
  "refreshCount": 2,
  "revoked": true,
  "events": [
    "refresh consumed -> new tokens issued",
    "refresh reuse -> session revoked",
    "business API -> 401"
  ]
}
```

## 배포에 대한 해석

현재 갱신 조율은 독립 BFF 인스턴스 사이에서 작동하지 않는다. replica 증설뿐 아니라 프로세스가 겹치는 배포에도 같은 위험이 적용될 수 있다. 실제 배포의 replica 수와 배포 중 겹침은 이 실험에서 확인하지 않았다.

단일 프로세스도 응답 유실 후 유예 만료까지 해결하지 못한다. 따라서 단일 프로세스 운영은 한 가지 경합을 제한하는 조건이지 모든 세션 단절을 막는 보장은 아니다. 공유 조율을 도입하더라도 갱신 성공 후 응답 유실, 작업 소유자 장애, 결과 보존을 별도로 설계해야 한다. 분산 락 하나로 전체 문제가 해결된다고 결론 내리지 않는다.

## 포트폴리오에 사용할 수 있는 설명

“기존 BFF의 프로세스 내부 갱신 공유를 검증하고, 독립 BFF 인스턴스 두 개와 토큰 재사용 폐기 규칙을 구현한 모의 백엔드로 세션 단절을 재현했다. 단일 인스턴스의 동시 20개 요청은 갱신 1회로 처리됐고, 인스턴스가 분리되면 중복 갱신으로 세션이 폐기되는 운영 제약을 확인했다.”

실제 수행·이해한 범위에 맞춰 사용한다. 이 결과를 실사용자 20명 부하 검증, 실제 Cognito 다중 서버 장애 재현, 분산 인증 문제 해결로 표현하지 않는다.
